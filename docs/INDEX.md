## What each benchmark tests

### `r01_reset_backward_barrier`

**Stressor.** A six-round invertible chain fed directly from primary inputs terminates at a synchronous-reset register whose downstream logic is trivial. There is no upstream register to push forward, so the only way to balance the register cut is to move the reset register BACKWARD into the chain -- which requires a new reset value equal to the pre-image of the original one.

**Expectation / result.** MEASURED: Genus solves this. With retiming enabled it reaches 325 MHz on the original, versus 240 MHz for the hand-retimed reference -- it beats the manual solution by 35%, because it restructures the arithmetic as well as moving registers, and it is willing to add registers (32 -> 42) to do it.

### `r02_reset_no_valid_init`

**Stressor.** Backward retiming across a reset flop where NO new reset constant can reproduce the original behaviour: the logic being crossed is not surjective onto the reset value. The only legal fix is to unmap reset into explicit reset circuitry, then retime the now-reset-free register.

**Expectation / result.** This is the case Touati and Brayton's forward-only restriction exists to avoid. Genus exposes retime_fallback_to_explicit_reset (default true), so it may well find this; the benchmark measures whether it does and what the extra flop costs.

### `r03_async_reset_blocker`

**Stressor.** Identical unbalanced shape to r01, but the register that must move backward has an ASYNCHRONOUS reset. On Artix-7 an async reset forbids control-set remapping outright; on gf180mcu it forces the dffrnq cell.

**Expectation / result.** Genus gates this on retime_async_reset (default true). Vivado's coding guidelines explicitly advise against async reset because control-set remapping becomes impossible, so the Artix-7 result is expected to be worse than r01's.

### `r04_init_only_no_reset`

**Stressor.** The same unbalanced chain as r01, but the registers carry only an initial value and there is no reset port at all. On Artix-7 the INIT attribute must travel with a retimed register; on an ASIC library there is no initial-value concept, so the retimer is unconstrained.

**Expectation / result.** This should be the EASIEST Class A case for Genus -- with no reset semantics to preserve, backward retiming is unconstrained. Vivado must instead recompute INIT. The benchmark exists to expose that FPGA/ASIC asymmetry directly.

### `r05_fsm_high_fanout`

**Stressor.** A one-hot FSM state register drives 48 datapath lanes as well as its own next-state logic. The state net is a very high fanout, physically long net. The reference clones the state register eight times, one clone per group of six lanes, keeping the original solely for next-state.

**Expectation / result.** The state register sits in a feedback loop, so classical retiming cannot move it. Duplication is the transform that helps, and duplication is outside the retiming formulation. Tools do clone for fanout during optimisation; the question is whether they clone as aggressively and as well-placed as the manual solution. Scored on post-route wirelength and Fmax.

### `r06_fsm_high_fanin`

**Stressor.** Sixty-four status bits are registered, then reduced by a deep tree, and the result feeds FSM next-state logic. The critical path is status_q -> reduce -> next_state -> state_q. The fix is to forward-retime the status register across the reduction so the reduction happens before the register, not after.

**Expectation / result.** A clean forward retiming that preserves latency exactly. The stressor is that the destination register is FSM next-state logic: Genus has retime_preserve_state_points, and tools are generally reluctant to disturb registers adjacent to a state machine.

### `r08_fsm_output_decode`

**Stressor.** The FSM's Mealy output decode, not its next-state logic, is the critical path. The decode is a pure feed-forward cone and is fully retimable, but tools tend to treat it as fused to the state machine.

**Expectation / result.** Legal strict retiming: split the decode and move the output register into its middle. The reference derives the moved register's reset value as a pre-image, since the second half of the decode is invertible.

### `r09_unbalanced_mult_pipe`

**Stressor.** A 16x16 multiply is computed entirely in pipeline stage 1, while stages 2 and 3 do almost nothing. Classical forward retiming should rebalance it.

**Expectation / result.** Both Genus and Vivado are expected to handle this; it is a positive control for the classical Leiserson-Saxe case. A tool that fails here is broken, not merely conservative.

### `r10_long_carry_chain`

**Stressor.** A three-level 32-bit adder tree is computed entirely in stage 1, stage 2 does one xor. Rebalancing requires moving a register across an adder, which forces the adder's OTHER operand to be delayed too.

**Expectation / result.** Legal forward retiming, but the reference has to add a 32-bit register for operand e. This illustrates why retiming across multi-input operators costs registers -- and why a tool minimising register count will decline it.

### `r11_deep_retime_distance`

**Stressor.** A 24-round invertible chain feeds three back-to-back registers. Balancing it requires moving registers 6, 12 and 18 logic rounds upstream -- a large retiming distance that tests effort limits rather than legality.

**Expectation / result.** Retiming is legal and the reference achieves roughly a 4x period reduction. Tools that cap retiming distance or effort will only partially close the gap.

### `r12_wide_reduction_tree`

**Stressor.** Sixty-four 8-bit values are summed by a full adder tree in stage 1; stage 2 does one xor. The fix pushes registers into the tree interior, registering four partial sums instead of one total.

**Expectation / result.** Textbook forward retiming into a reduction tree. Both tools should manage it; included to measure how much period they recover versus the reference's clean four-way split.

### `r13_retime_around_sram`

**Stressor.** A deep address computation feeds a synchronous-read memory. The register that must move is the one driving the memory's address port. Memories are hard boundaries: on ASIC the macro timing model is fixed, and on Artix-7 the address register is normally absorbed into the BRAM itself, so moving it away costs that absorption.

**Expectation / result.** The move is a legal strict retiming of the address path, but its destination register directly drives a memory address pin. Tools avoid restructuring at macro pins. On Vivado the interesting question is whether moving the register defeats BRAM address-register absorption.

### `r15_hier_boundary_block`

**Stressor.** A purely combinational deep submodule feeds a submodule whose first act is to register its input. The critical path runs from primary inputs, through all of submodule A, to a register that lives in submodule B. Fixing it requires moving that register BACKWARD ACROSS THE MODULE BOUNDARY into A.

**Expectation / result.** Legal strict retiming, but it relocates a register from one module to another. Tools that keep hierarchy boundaries intact -- or that retime only within a module -- cannot express it. Also tests whether boundary optimisation is enabled by default.

### `r16_dont_touch_conflict`

**Stressor.** A register in the middle of the pipeline is marked dont_touch/preserve, and it is on the critical path. It cannot be moved, but the registers around it can. The correct answer is to rebalance using the movable registers and accept the pin, not to give up on the design.

**Expectation / result.** Tests whether a retimer degrades gracefully. The pinned register caps the achievable period below the unconstrained optimum, but a useful improvement is still available by moving the output register backward. A tool that bails out entirely when it meets a preserved register scores worst here.

### `r17_clock_enable_barrier`

**Stressor.** An unbalanced two-stage pipeline whose registers both carry a clock enable. Rebalancing requires moving a register whose enable term must move with it. gf180mcu has no enable flop at all, so the enable becomes a recirculating mux and the register to be moved sits inside a mux loop.

**Expectation / result.** Genus exposes retime_move_mux_loop_with_reg for exactly this situation; whether it fires is the question. On Artix-7 the enable maps to FDRE.CE, where moving the register means re-deriving the enable.

### `r18_clock_gated_region`

**Stressor.** A three-stage enabled pipeline that the flow clock-gates (lp_insert_clock_gating is enabled for this benchmark via common.tcl, so a real ICG cell is inserted and shared across the region). Rebalancing the stages moves registers inside the gated domain, which changes which flops the ICG drives.

**Expectation / result.** Retiming and clock gating interact: moving a register changes the gated flop count and therefore the ICG's own load and enable fanout. Tools sequence clock-gating insertion and retiming as separate passes, so the second one sees the first one's decisions as fixed.

### `r19_power_activity_retime`

**Stressor.** Two register positions that are nearly timing-equivalent but differ enormously in switched capacitance: 64 high-activity flops before a reduction tree, versus 8 low-activity flops after it. Retiming across the reduction is legal and latency-preserving.

**Expectation / result.** No production tool retimes for switching activity, so both Genus and Vivado are expected to leave the registers where the RTL puts them. Scored on power at a period both variants meet, not on Fmax.

### `r20_glitch_absorb`

**Stressor.** A deep XOR network feeds a wide 32-lane cone in the same pipeline stage, so the XOR network's glitches propagate through all 32 lanes. Moving the register to sit immediately after the XOR network absorbs the glitching before it fans out.

**Expectation / result.** Strictly latency-preserving and roughly timing-neutral, but it removes glitch propagation into 32 lanes of logic. No production tool places registers to absorb glitch power. Scored on switching power from an activity-annotated run.

### `r21_wire_pipeline_cross_die`

**Stressor.** Two large logic clusters joined by a 64-bit bus. After placement the bus is physically long and its wire delay, not logic, sets the period. The fix is to pipeline the bus, which ADDS a cycle of latency and is therefore NOT a legal retiming.

**Expectation / result.** LATENCY-CHANGING: the reference adds one pipeline stage, so orig and retimed are equivalent only up to a one-cycle skew. No tool may do this on its own, and none should. It is in the suite to quantify what a latency-relaxing physical transform is worth, since that is the transform a placement-driven retimer would want and cannot legally take.

### `r22_fanout_wire_load`

**Stressor.** The scaled-up version of r05. A 6-bit control register drives 256 datapath lanes at low placement density, so the driven net genuinely spans the die and its load is dominated by wire capacitance rather than pin capacitance. The reference clones the driver 16 times, one per group of 16 lanes.

**Expectation / result.** r05 showed that 8-way cloning of a 48-lane fanout in a 479-cell design LOSES: +39% wirelength and +52% power for 66 ps. This benchmark exists to find the size at which the trade reverses, since cloning can only pay off once the loads are far enough apart that one long net becomes several short ones. Density is deliberately low (0.35) to spread the die.

### `r24_loop_bound_control`

**Stressor.** A single-register feedback loop containing all the logic. The iteration bound equals the loop delay, so NO retiming can reduce the clock period. The retimed variant is deliberately identical to the original.

**Expectation / result.** Neither tool should improve on this, and the reference cannot either. Because orig and retimed are the same circuit, the measured difference between them is pure tool noise -- which is what this benchmark is for: establishing the noise floor against which the other benchmarks' gains are judged.

### `r26_sdc_exception_invalidation`

**Stressor.** A multicycle-path exception is declared by register name on the stage-2 path. When the retimer relocates those registers it renames them (Genus calls them retime_*), the exception stops matching anything, and the relief the designer intended silently disappears.

**Expectation / result.** DIAGNOSTIC benchmark. The measurement is whether the SDC exception still matches objects after retiming, not Fmax. This is a practical reason engineers fight retimers: the transform is correct but it invalidates name-based constraints, and nothing warns loudly.

### `r27_exception_scope_probe`

**Stressor.** Two independent pipelines in one design. Pipeline A is unbalanced and needs retiming, and no constraint names its registers. Pipeline B carries a multicycle-path exception naming its own registers. The probe: does Genus still retime A?

**Expectation / result.** Answers the scope question r26 raises. If A is retimed, exception-driven exclusion is path-local and the workaround is to keep exceptions off retimable paths. If A is NOT retimed, one exception anywhere disables retiming design-wide, which is a much more serious constraint on how a design can be written.

### `r28_congestion_wire_split`

**Stressor.** Two logic clusters joined by a 64-bit bus, placed at 0.90 density with a central placement blockage and the signal routing stack capped at Metal3, so the bus crossing is long and congested. The movable register decides how much logic sits before the crossing versus after it.

**Expectation / result.** This is the regime the project cares about: net delay W comparable to or greater than logic delay. A wire-blind retimer balances logic evenly (a=b) and gets period L/2+W. The wire-aware optimum is ASYMMETRIC (a=b+W), giving (L+W)/2 -- better by W/2. The original IS the even split a wire-blind retimer produces, so the benchmark measures that gap directly.

### `r29_wide_crossing`

**Stressor.** Two logic clusters joined by a 512-bit crossing, ~10k cells so the die is large enough for the crossing to cost real delay. Eight nonlinear rounds are split between the clusters and the movable register decides how many sit on each side. This is r28's structure at r22's scale: r28 has the right shape but only ~800 cells, so its die is tens of microns across and it needs a Metal3 cap, a placement blockage and a 4:1 core to reach 15% route share -- returning just 18 ps. r22 reaches 15.3% route share unaided at 12.6k cells but is a fanout benchmark, with no movable crossing to retime.

**Expectation / result.** With the crossing costing W, the two cycles are a and W + b, so the balance point is a = b + W rather than a = b. The original IS the even split a wire-blind retimer produces, giving period W + 4r; the reference moves two rounds ahead of the register for max(6r, W + 2r). Predicted gap is about W/2, so the benchmark is only informative once W exceeds roughly two rounds -- the measured route share decides whether it says anything, and that is checked before any conclusion is drawn. Scored on post-route Fmax at equal density, with congestion overflow reported so a strangled unroutable design is not mistaken for a fast one.

### `r30_fsm_decode_fanout`

**Stressor.** Reduced from sifferman/ternip rtl/fus/ternip_tmatmul.sv at commit 55bf227, which Vivado could not retime; commit 7b658c7 did the transform by hand. A 3-state FSM plus a 4-value operation enum are decoded into five mutually exclusive conditions, each gating a 32-lane x 32-bit accumulator array. The decode output is the high-fanout net and it sits in front of everything it gates. state_q is in the next-state feedback loop, so classical retiming cannot move it; the legal transform is to retime the DECODE across the state register, which needs the decode of the reset state as the new registers' reset value. This is the only benchmark in the suite taken from a real design rather than constructed.

**Expectation / result.** The reference moves the decode cone off the critical path and turns a high-fanout decode apex into a register output the tool may duplicate per lane group. Vivado did not find this on the real design. The open question for this suite is whether Genus does, and whether the win is a logic-depth effect or a wire effect -- the fanout net is physically long, so post-route wirelength and reg-to-reg slack are both reported.

### `r31_clone_distinct_reset`

**Stressor.** A 5-bit phase counter in its own feedback loop drives 24 lanes, each decoding the phase through a different 3-level mask function. Classical retiming cannot move the counter (the loop's register count is invariant) and relieving the fanout needs duplication, which is not a retiming move. The reference clones the decode per lane and registers it, so each clone needs its OWN reset constant -- lane_mask(i, 7) for reset phase 7. Generalises r30, which comes from a real Vivado failure but where the registered decodes happened to share a reset value.

**Expectation / result.** A tool that clones for fanout but resets every clone identically is correct in steady state and wrong for the cycles after each reset, so this is as much a correctness probe as a QoR one: scripts/gen_tb.py pulses reset mid-run and scripts/formal_equiv.py proves the pair by BMC. Scored on post-route wirelength and reg2reg TNS at a stress period, since the fanout net is physically long.

### `r32_backward_reset_preimage`

**Stressor.** A 256-bit pipeline split 8 levels / 2 levels, so balancing requires moving the middle register BACKWARD by three levels. Those three levels contain an AND-mask, so the stage is not surjective, and the register's reset value is provably outside its image (the stage is linear over GF(2); Gaussian elimination on the 256x256 matrix decides it). No constant can serve as the moved register's reset value, so a behaviour- preserving backward move MUST add explicit reset logic -- which is what Genus does when retime_fallback_to_explicit_reset keeps its TRUE default, at the cost of a 256-bit mux level.

**Expectation / result.** Three outcomes are all interesting. The tool may decline to move the register at all (retime_optimize_reset defaults to FALSE), leaving the 8/2 split. It may move it and add explicit reset logic, in which case the question is whether it recovers the balance net of the mux. Or it may move it and get the reset value WRONG, which the mid-run reset pulse in gen_tb.py and the BMC proof in formal_equiv.py will catch.
